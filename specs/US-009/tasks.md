# Implementation Tasks: US-009 — Administrator Login Error Handling

## Functional Requirements Implementation

### T001: FR-001 — Generic Failure Messages Without Credential Differentiation
**Requirement**: The login endpoint must validate administrator credentials and, upon validation failure, return a generic error message that does not differentiate between invalid username and invalid password, nor reveal which credential field failed validation.

**Affected components**:
- `login` (1036)
- `LoginErrorResponse` (1550)
- `LoginRequestDto` (1484)

**Acceptance criteria**:
- US-009-ac-1: Given an administrator enters invalid credentials, When the login is submitted, Then a generic failure message is displayed without revealing which credential was incorrect

**Implementation notes**:
- Grounded in provider-object:1036, provider-object:1550, provider-object:1484
- Must ensure credential field names are not exposed in error responses
- Error message must not differentiate between invalid username and invalid password
- Prevent account enumeration attacks

---

### T002: FR-002 — Account Status Notifications for Locked/Disabled Accounts
**Requirement**: The login endpoint must detect when a user account is in a locked or disabled state and return an appropriate notification message that communicates the account status without exposing other sensitive account metadata.

**Affected components**:
- `login` (1036)
- `LoginRequestDto` (1484)
- `LoginErrorResponse` (1550)

**Acceptance criteria**:
- US-009-ac-2: Given a user with a locked or disabled account attempts login, When the login is submitted, Then an appropriate notification indicating the account status is displayed

**Implementation notes**:
- Grounded in provider-object:1036, provider-object:1484
- Database object query returned empty; requires database schema inspection
- Must verify account status checks (locked/disabled) are performed
- Status-specific notifications must not leak sensitive account metadata
- Bias flag: protected characteristics mentioned (disabled) — verify they are required by the source requirement

---

### T003: FR-003 — Role-Based Access Control Enforcement
**Requirement**: The login endpoint must enforce role-based access control such that non-administrator users attempting to access the administrator login endpoint receive an unauthorized error message and are denied access.

**Affected components**:
- `login` (1036)
- `DefaultLoginGuard` (3003)
- `LoginGuard` (1467)
- `createAuthRouter` (2428)

**Acceptance criteria**:
- US-009-ac-3: Given a non-admin user attempts to access the Admin Login, When authentication is attempted, Then access is denied with an unauthorized message

**Implementation notes**:
- Grounded in provider-object:1036, provider-object:3003, provider-object:1467, provider-object:2428
- CAST identifies two guard transactions (DefaultLoginGuard, LoginGuard) in the call graph
- No structural evidence confirms role-based access control (admin vs. non-admin)
- Requires inspection of guard implementations and login_error to verify non-admin access is denied
- Verify guard enforcement order in createAuthRouter

---

### T004: FR-004 — Authentication Service Unavailability Handling
**Requirement**: The login endpoint must detect when the Authentication Service is unavailable (e.g., timeout, connection failure, or service error) and return a service unavailable message to the client.

**Affected components**:
- `login` (1036)
- `LoginErrorResponse` (1550)

**Acceptance criteria**:
- US-009-ac-4: Given the Authentication Service is unavailable, When login is attempted, Then a service unavailable message is displayed

**Implementation notes**:
- Grounded in provider-object:1036, provider-object:1550
- CAST provides no structural evidence of service availability checks, circuit breaker patterns, or timeout handling
- No database objects, exception handlers, or external service calls visible in measured facts
- Requires implementation inspection to confirm Authentication Service unavailability is detected
- Service unavailable message must not expose internal service names, versions, or infrastructure details

---

### T005: FR-005 — Information Disclosure Prevention Across All Error Scenarios
**Requirement**: All error responses generated by the login endpoint across all failure scenarios (invalid credentials, locked/disabled account, unauthorized access, service unavailability) must not expose credential field names, password patterns, account enumeration vectors, or other sensitive information that could enable account enumeration, timing attacks, or side-channel inference.

**Affected components**:
- `login` (1036)
- `LoginErrorResponse` (1550)
- `LoginRequestDto` (1484)
- `§{main_sources}§/New_Prompt_UMS-develop/BACKEND/src/controllers/auth.controller.ts`

**Acceptance criteria**:
- US-009-ac-5: Given any login failure scenario, When the error is displayed, Then no credential hints or sensitive information are exposed

**Implementation notes**:
- Grounded in provider-object:1036, provider-object:1550, provider-object:1484
- CAST confirms login_error and LoginErrorResponse exist but provides no intra-object structural analysis
- Cannot verify whether credential hints, password patterns, account enumeration vectors, or other sensitive information are leaked
- Requires code-level review of all error paths in login_error to audit for information disclosure
- Must ensure error messages are consistent and generic to prevent timing attacks or side-channel information leakage
